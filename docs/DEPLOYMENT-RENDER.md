# Deployment and operations

[`render.yaml`](../render.yaml) defines the deployment from the root of `kriscodes/portfolio`, with automatic deployment after CI checks pass. It provisions a static site, an always-on paid API, and PostgreSQL. Keep the repository root as each service's build root because the API depends on the shared workspace package.

| Resource                         | Configuration                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------- |
| `kristian-salmeron-web`          | Static site; publishes `apps/web/out`                                                 |
| `kristian-salmeron-api`          | Node web service; `0.5c-512mb` plan; Oregon; starts `node apps/api/dist/server.js`    |
| `kristian-salmeron-analytics-db` | PostgreSQL 18; `0.1c-256mb` plan; 1 GB disk; Oregon; no external IP allowlist entries |

The Blueprint pins Node 22.23.2 and pnpm 11.22.0. Both builds install with `--frozen-lockfile --prod=false`; the frontend builds `@kristian/web`, while the API builds `@kristian/api...` to include its dependencies. API health checks use `/api/v1/health`. The process reads Render's `PORT` and binds to `0.0.0.0`.

## Configuration

| Variable                       | Where and why                                                                            |
| ------------------------------ | ---------------------------------------------------------------------------------------- |
| `DATABASE_URL`                 | API; private connection string supplied by the Blueprint database reference              |
| `ANALYTICS_OWNER_EMAIL`        | API; configured owner address, supplied in Render                                        |
| `ANALYTICS_SETUP_TOKEN`        | API; independent random secret of at least 32 characters; generated by the Blueprint     |
| `ANALYTICS_HASH_SECRET`        | API; independent random secret of at least 32 characters; generated by the Blueprint     |
| `ANALYTICS_ORIGIN`             | API; `https://analytics.kristiansalmeron.com`                                            |
| `NEXT_PUBLIC_ANALYTICS_ORIGIN` | Frontend build; public collector origin, set to `https://analytics.kristiansalmeron.com` |

Preserve existing secrets and the database when updating an installation. Changing the hash secret breaks continuity with stored identifier hashes. Never put credentials or database URLs into `NEXT_PUBLIC_*` variables, source files, or build artifacts.

For local analytics development, use the names in [`.env.example`](../.env.example), a local database, and a local collector origin. Load API values into the process environment before starting it. Production requires complete analytics configuration and a reachable database; a missing store prevents startup.

## Release workflow

Use the same process as Lab and Toolbox: create a regular feature branch, open a pull request, wait for CI, then merge into `main`. GitHub Actions runs `pnpm validate` on every pull request and push to `main`, including PostgreSQL-backed tests. Render waits for the deployed commit's checks with `autoDeployTrigger: checksPass`; failing checks or zero detected checks block automatic deployment. Do not add workflow path filters that skip CI on deployable commits.

Each service's build filter includes its app, shared packages, dependency lockfile, runtime and workspace configuration, and scripts. Website-only changes do not deploy the API, and API-only changes do not deploy the website. Documentation-only changes run CI without triggering application deploys. Keep the filters in sync when adding build inputs.

`render.yaml` is the source of truth for service settings. The Blueprint tracks `main` with Auto Sync enabled. Blueprint configuration syncs and manual deploys are separate from commit-triggered deployments. Review configuration changes and merge only after PR checks pass. Manual releases are for recovery after verifying the selected commit's checks. After deploying a specific commit, restore **After CI Checks Pass** if Render disabled auto-deploy. Routine releases do not use deploy hooks.

## Deployment

1. Connect `kriscodes/portfolio` to a Render Blueprint using `render.yaml` and the `main` branch. Review the provisioned plans and supply the owner email.
2. Deploy the API before clients that require a new collector or event schema. Schema initialization runs before production starts serving requests.
3. Use the static site's custom-domain settings for `kristiansalmeron.com` and the API's settings for `analytics.kristiansalmeron.com`. Apply the DNS records shown by Render and verify HTTPS.
4. Keep the static export's per-route HTML. Do not rewrite every request to `/index.html`. Preserve the social-link redirects already defined in the Blueprint.

For a new installation, open `https://analytics.kristiansalmeron.com/#setup=SETUP_CODE` using the generated setup token and choose a password of 14–128 characters. The page removes the token from the visible URL. Setup closes after the owner exists; normal deployments retain the account and sessions.

## Verification

Before deployment:

```sh
pnpm validate
pnpm format:check
node scripts/test-insights-browser.mjs
```

The browser check needs Playwright. `PLAYWRIGHT_MODULE` and `PLAYWRIGHT_CHANNEL` can select an installed runtime/browser. Set `ANALYTICS_TEST_DATABASE_URL` only to a disposable test database for persistence and legacy-migration tests.

After deployment:

```sh
node scripts/test-live-web.mjs https://kristiansalmeron.com
```

Also verify API health, `/api/v1/projects`, `/analytics-assets/tracker.js`, the dashboard login, and unauthenticated report rejection. Check the frontend at a nested route and an unknown URL; confirm the latter returns HTTP 404. Use browser opt-out for manual production checks so they do not inflate reports. Observe delivery through the owner dashboard; serving the collector asset alone does not prove events arrive.

## Recovery

Use Render deployment history to roll back application code after checking schema compatibility. Existing migrations are additive and do not delete legacy events; rolling back code does not undo collected data or restore expired events. Database backups and restoration are managed separately from application rollback.

For owner-password recovery, run `node apps/api/dist/analytics/reset-owner.js` in the private API service shell with the new password on standard input. Do not pass it as an argument. The command requires `DATABASE_URL` and `ANALYTICS_OWNER_EMAIL`, updates the existing owner, and revokes all sessions.

A 503 health response points to analytics configuration or database readiness. For failed builds, check the pinned runtimes, repository-root build directory, frozen lockfile, and installation of build-time dependencies. For incomplete reports, check privacy exclusions, collector requests, date ranges, and coverage indicators before treating missing data as zero activity.
